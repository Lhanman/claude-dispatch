规格里的缺口，到实现阶段才发现是最贵的：要么返工，要么带着猜测往下写。动手前用一点小开销把缺口找出来。

## 1. 只写决策，不写实现

方案、规格、任务里记录**实现者需要的决定**，不转录代码：

- 测试步骤：测试叫什么、断言什么。
- 代码步骤：文件、函数签名、规格里的数值和文案（原样抄，不改写）。函数体只在规格决定不了的算法上写几行。
- 引用别的任务产出的东西，写那个任务的接口，不重复它的实现。

自检一下篇幅：方案比需求原文长好几倍，多半是在转录代码，把函数体换成签名加断言。

## 2. 审查重点（L2、L3 都做）

在方案或规格末尾加一节「审查重点」，**最多 5 项**：规格暗示了、却没有任何任务的测试覆盖的输入或失败模式。常见的几类：空值或缺省、边界、重复调用或重入、并发、旧格式的数据、权限不足、依赖失败。

每一项写明由哪个任务的哪条测试来钉住；没有对应测试就补一条进那个任务。找不出就写「无」，不要凑数。

## 3. 实现者视角通读（只在 L3）

规格不到一屏、任务不足 3 项时跳过（这样的任务本来就该降级）。

派一个全新上下文的子 agent，**显式指定模型**，省略会继承主会话的模型：

- `subagent_type`: `general-purpose`
- `model`: `sonnet`
- 不用 `dispatch:reviewer`：它审的是代码差异，不是规格。

委托：

```
你是要实现下面这份规格的工程师，还没有开始动手。只读，不修改任何文件。

规格：<change 目录路径>（proposal、design、tasks、specs 都读）

列出开工前你还得问的问题，分两类：
- 阻塞：答案会改变做出来的东西
- 次要：你自己能定，但应该让人知道

每条一行：问题 + 你猜的答案。总长不超过 20 行；没有就写「无」，不要凑。
不评价设计好坏，不提实现建议。读代码只用来判断某个问题是不是已经被规格回答了。
```

收到回传后：

1. 能从规格或代码里查到答案的，自己答，并把答案补进规格。
2. 次要问题自己定，在规格里标「（我定的）」。
3. 阻塞问题合成**一轮**，连同规格一起交给用户审，不要一个一个问。

开销约一次 Sonnet 子 agent 的读取（估计 15–20k token），换的是用户少一两轮来回，以及实现中途不因规格缺口返工。

## 常见借口

| 借口 | 实际情况 |
|---|---|
| "规格我刚写的，不用再读" | 你带着自己的意图读，看不到缺的部分；实现者没有你的意图。 |
| "审查重点想不出来，随便列几条" | 凑数会把真正的缺口淹掉。想不出就写「无」。 |
| "把函数体也写进规格，实现更快" | 规格变成代码的第二份拷贝，改一处要改两处，还把审规格的人拖进读代码。 |
