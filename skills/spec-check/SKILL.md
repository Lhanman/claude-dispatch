规格是写规格的人写的，天然觉得自己写清楚了。让一个没参与讨论的人按它"假装开工"，能在写代码之前就暴露缺口。这一步花一次子 agent 的钱，省的是做到一半才发现规格有洞的返工。

## 什么时候做

- L3：`/opsx:propose` 写完规格后、交给用户审阅之前，做一次。
- L4：拆出的每个子 L3 各做一次。
- L2 不做：方案已经在 Plan 模式里交给用户审过。

## 怎么派

派 `dispatch:spec-checker`，委托里只写两段：

```
## 规格在哪
[openspec/changes/<名字>/ 下的文件路径；没有 OpenSpec 时是 docs/plans/ 里的方案文件]

## 代码在哪
[规格涉及的目录或文件，让它能核对规格引用的接口是否存在]
```

不要给：对话历史、你对规格的自评、"我担心这里不清楚"。它要的是一个干净的视角。

## 怎么处理回来的问题

读完全部再动手。把每条问题归入三类：

1. **现有材料里能找到答案**（grill-me 的结论、代码、已有笔记）：把答案补进规格，不打扰用户。
2. **次要的**（不同选择对用户可见的结果没有影响）：自己选定，在规格里写明"此处为实现时的默认选择：……"。
3. **会改变做出什么或怎么验收的**：留给用户。

补完之后把第三类问题**一次问完**：按影响从大到小排序，每条附 spec-checker 给的倾向或你的推荐答案。同时告诉用户第 2 类里你替他选了什么，让他有机会推翻。

用户回答后更新规格，再交给用户审阅。**不要**为了确认补得对不对再派一次 spec-checker。

## 红线

- 把第三类问题自己拍板，不告诉用户。
- 一条条分多条消息问，而不是一次问完。
- 规格没补完就让用户审阅，让用户替你发现 spec-checker 已经指出的缺口。
