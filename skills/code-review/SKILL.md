审查的价值来自"没看过实现过程"。reviewer 拿到的必须是精心裁剪的上下文，不是你的会话历史。

**核心原则：早审、常审。一次审查只买一个独立视角，别把它污染掉。**

## 什么时候派

**必须派：**
- L2 实现完成、验证通过之后，派一次。
- L3 每个任务组做完派一次；交付前终审一次，调用时指定 `model: opus`。
- L4 每个子 L3 各自走完上面一整轮。

**值得派：**
- 同一个问题修了两轮没好（先转 `dispatch:systematic-debugging`，仍不行时借一次独立判断）。
- 大重构之前，先审一次现状当基线。

**不派：** L0、L1。这两级靠验证命令兜底，派子 agent 的开销超过收益。

## 先验证，再派审查

reviewer 不跑测试。验证没过就派，等于用它的上下文换一份你本来就知道的失败。先 `dispatch-verify <命令>`，绿了再派。

## 取改动范围

```bash
BASE=$(git rev-parse HEAD~1)     # 或任务组开始时的 SHA、origin/main
HEAD=$(git rev-parse HEAD)
git diff --stat $BASE..$HEAD     # 先自己看一眼规模，确认范围没跑偏
```

改动还没提交时，说明范围是工作区加暂存区，并列出在范围内的文件。项目不是 git 仓库时，只给文件清单。

## 怎么写委托

委托里写四段，别的都不要：

```
## 做了什么
[两三句话：实现了哪个能力，动了哪些模块]

## 需求是什么
[L3：规格文件路径 + 任务组编号。L2：Plan 模式里定下的方案原文]

## 审查范围
git diff <BASE>..<HEAD>
[或：未提交的改动，涉及 <文件清单>]

## 已经验证过什么
[跑了哪些命令、结果如何]
```

- **需求那一段决定审查质量**。reviewer 只能靠它判断"有没有做到"，写模糊了它就只能评风格。手上只有口头需求时，照原话写进去，不要替它总结。
- **写明已验证的部分**，免得它重复怀疑已经确认过的地方。
- **不要给**：会话历史、你的思考过程、试过又放弃的方案，尤其不要给"我觉得这里可能有问题"。这句话会把它的注意力钉在你的猜测上，漏掉你没想到的地方。

`dispatch:reviewer` 自带职责边界和回传格式（结论 / 问题 / 没能验证的，总长不超过 40 行），委托里不用重复。

## 处理审回的意见

读完全部再动手，不要读一条改一条。

1. **逐条对着代码验证。** reviewer 没有完整上下文，它可能不知道某处是为了兼容旧数据才那么写的。
2. **给每条定处置：**
   - **必须改**：会出错、崩溃、数据损坏、竞态、安全问题，或明确的需求遗漏。改完才算完成。
   - **建议改**：有道理但不影响正确性。当前级别装得下就改；装不下就记进笔记或 issue，并在回复里告诉用户。
   - **不改**：验证过是误报，或者违背项目已有的决策。回复里写清技术理由。
3. **有一条看不懂就先问**，别先改看懂的那几条。几条意见常常互相关联，只改一半会改出更糟的状态。
4. **一条一条改，每条各自验证。** 批量改完再一起跑，出了问题分不清是哪条引起的。
5. **全改完再跑一次完整验证。**

审查结论是"需要修改"时，它不是建议。要么改掉，要么向用户说明为什么不改。

## 怎么回应

不要写"你说得对""说得好""感谢指出"。审查是技术判断，不需要社交表演：意见对就直接改，然后说改了什么。

- 对：`已修：exporter.py:88 的边界判断改为闭区间，补了越界测试。`
- 对：`第 3 条不改：这个分支给 0.4 之前的配置格式兜底，tests/test_config.py:40 覆盖了。`
- 不要：`你说得对！我马上改。`

自己反驳错了，一句话说清就改：`查过了，空列表时确实会抛异常，我之前看漏了分支。已修。` 不用长篇道歉。

## 常见借口

| 借口 | 实际情况 |
|---|---|
| "改动很简单，不用审" | 简单的改动一样会写错边界、漏掉需求。判成 L2 就说明有风险信号。 |
| "我自己看一遍 diff 就行" | 你是实现者，看到的是自己的意图；而且读整份 diff 会吃掉后面执行要用的上下文。派出去，只有结论回来。 |
| "先派审查，让它顺手把测试问题一起找出来" | reviewer 不跑测试。验证没过就派，是拿它的上下文换你已知的失败。 |
| "把会话历史贴给它，它才看得懂" | 它要看的是改动和需求。贴历史只会把它的判断拉回你的思路里。 |
| "意见看着不对，先按它说的改了再说" | 先验证。改掉一处正确的兼容逻辑，比留下一条误报更贵。 |
| "问题都记下了，下次再说" | 「必须改」的问题不能顺延。顺延就是把验证没过说成完成。 |

## 红线

- 验证没过就派审查，或者验证没过就声称完成。
- 「必须改」的问题没改完就进入下一个任务组。
- 结论是"需要修改"，却只记下不改、也不告诉用户。
- 把审查意见当命令照改，不先对着代码验证。
