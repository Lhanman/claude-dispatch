把这次工作里值得保留的内容，写成知识库里的一篇笔记。

以后检索时，只会先读每篇笔记 frontmatter 里的一行摘要和标题大纲，再按需打开某一节。所以格式必须统一：摘要要能单独说明问题，结论要放在最前面。

## 1. 确定写哪个库、哪个子目录

两个库互不检索，选错会让另一边的检索多出无关结果：

| 库 | 记什么 | 怎么定子目录 |
|---|---|---|
| **工程知识库** | 跟着代码、项目、工具走的：方案、决策、踩坑、指南 | 项目 CLAUDE.md 的「dispatch 知识库」一节；没有就用项目名 |
| **个人笔记库** | 跟着人走的：经历、习惯、计划、学习、复盘 | 按主题取，如 健康、理财、读书、日常 |

分不清时问用户，不要自己猜。

- **工程库**：执行 `dispatch-kb path`。没配置时，告诉用户在 `~/.claude/dispatch/config` 写入 `kb_dir=<目录>`，然后停止。
- **个人库**：执行 `dispatch-kb personal-path`。没配置时，告诉用户在同一个文件里写入 `personal_dir=<目录>`，然后停止。这个库是可选的，用户没配就别劝他配。
- **子目录**：用 `dispatch-kb dirs`（个人库加 `--personal`）看现有的顶层目录，优先复用；没有对应的就按项目名或主题新建一个，在第 3 步和用户一起确认。
- **查重**：执行 `dispatch-kb search <主题关键词> [-d <子目录>]`（个人库加 `--personal`）。已有同主题的笔记时，问用户是更新原文还是新建一篇。不要另存成「修订版」「v2」之类的副本。

## 2. 起草

先按所在的库选类型，再按对应的小节顺序写。

**工程知识库**：

| type | 用途 | 小节（按顺序） |
|---|---|---|
| 方案 | 设计或实现方案 | 结论 / 背景 / 方案 / 决策记录 / 相关 |
| 决策 | 一次取舍 | 结论 / 背景 / 备选与取舍 / 影响 / 相关 |
| 踩坑 | bug 或问题的根因 | 结论 / 现象 / 根因 / 解决 / 如何避免 / 相关 |
| 指南 | 使用、接入或操作步骤 | 结论 / 步骤 / 常见问题 / 相关 |

**个人笔记库**：

| type | 用途 | 小节（按顺序） |
|---|---|---|
| 记录 | 发生了什么：经历、状态、习惯 | 结论 / 经过 / 细节 / 相关 |
| 计划 | 打算做什么、怎么安排 | 结论 / 目标 / 步骤 / 取舍 / 相关 |
| 学习 | 学到的东西 | 结论 / 要点 / 来源 / 相关 |
| 复盘 | 一件事做完回头看 | 结论 / 经过 / 做对的 / 做错的 / 下次怎么做 / 相关 |

每篇都必须以下面的 frontmatter 开头：

```markdown
---
title: 订单导出改为分批流式写出
type: 方案
project: 订单系统
summary: 导出超过 1 万行时按 2000 行分批流式写出，内存峰值从 1.2G 降到 150M，接口不变
tags: [订单导出, 流式写出, 内存, ExportService]
slug: order-export-streaming
created: 2026-09-19
updated: 2026-09-19
source: dispatch
---

# 订单导出改为分批流式写出

## 结论
- ……
```

写作要求：

- **`project` / `topic`**：工程库写 `project: <项目名>`，个人库把这一行换成 `topic: <主题>`。其余字段名一致。
- **summary**：一句话，不超过 60 字，要同时包含检索会用到的关键词和结论本身。检索结果里只显示这一行。
- **tags**：3–6 个，用真实术语——工程库用类名、模块名、协议名、错误码；个人库用人名、地点、身体指标、书名这类以后会想起来查的词。
- **slug**：2–4 个单词的英文短名，只用小写字母、数字和连字符。这篇笔记同步到文档站后，它就是网址 `/kb/<slug>/`；以后改标题、改文件名，网址都不变。**只有工程库需要**，个人库不同步，这一行可以省略。
- **不想公开的笔记**：在 frontmatter 里加一行 `publish: false`。它照样参与本地检索，但不会同步到文档站；已经上线的会在下次同步时下线。个人库不需要这一行。
- **标题**与文件名一致，写主题本身，例如 `订单导出改为分批流式写出.md`。不加日期前缀，日期写在 frontmatter 里。
- **「## 结论」**：3–5 条。读者只读这一节就应该能用上。记录类笔记里，它就是「这件事的要点」。
- **篇幅**：每篇不超过 150 行；超出就按主题拆成几篇，用 `[[笔记名]]` 互相链接。
- **内容**：只写事实和结论，不写过程（不出现「刚才」「这次会话」）；不贴大段代码，用 `路径:行号` 指向代码。个人库不写代码。
- **「## 相关」**：工程库列代码位置、OpenSpec 变更名、提交号和相关笔记 `[[…]]`；个人库列相关的人和事，以及相关笔记 `[[…]]`。

起草完成后，如果已安装 `humanizer-zh`，按它的规则润色一遍正文：只改散文，frontmatter、标题、代码、路径和 `[[…]]` 链接保持原样，不增删事实。然后进入第 3 步。

## 3. 给用户确认

写入前，把以下内容给用户看：写入哪个库、目标路径、title、type、summary、tags，以及「结论」各条。用户确认或修改后才写入；用户没有明确同意，就不写。

## 4. 写入

用 Write 写入文件，子目录不存在时一并创建。不改动知识库里的其他笔记，也不在知识库里执行 git 操作，除非用户要求。

## 5. 同步到文档站（只对工程知识库）

个人笔记库不参与这一步，直接跳过。

笔记所在的顶层目录在 `kb_public` 白名单里时（`dispatch-pages kb-sync --dry-run` 会显示白名单），执行：

```bash
dispatch-pages kb-sync
```

用户已授权自动发布，不用再问。同步是全量的：这一次会把所有公开笔记的变化一起带上。报告里「未上传」的篇目要原样转述给用户，不要为了让它通过而改写笔记内容，也没有放行开关。没有配置 `kb_public`、或这篇笔记不在白名单目录里，就跳过这一步，不用提。

写完后只回：写入的路径，以及同步后的网址（如果同步了）。
