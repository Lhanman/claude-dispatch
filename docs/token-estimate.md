# L2 / L3 的 token 开销估算

**这是自底向上的估算，不是实测。** 所有数字都是假设；用 `dispatch-usage` 在真实会话上量过之后，应以实测为准并回头改这份文档。

比较对象：**同一个任务，不用工作流，一个会话直接做完**。

单位：千 token（k）。
- **新增**：新进入上下文的内容加模型生成的内容。与价格无关，可以直接比较。
- **额外轮数**：主会话比基线多出的轮数。每一轮都要重读整个上下文（缓存读取），单价低，但在长会话里量最大。

## 基线假设

| | 新增 | 轮数 | 平均上下文 | 缓存重读 |
|---|---|---|---|---|
| L2 任务（跨模块改动） | 90k | 25 | 45k | 约 1,125k |
| L3 任务（一个完整特性） | 260k | 70 | 70k | 约 4,900k |

## L2 额外开销

| 步骤 | 执行者 | 新增 | 额外轮数 |
|---|---|---|---|

| grilling 一轮 | 主 | 1.5 | 1 |

结果：新增约 1.4 倍（乐观 1.2、悲观 1.8），缓存重读约 1.6 倍。

它换来的是：少一两轮规格上的来回，以及实现中途不因规格缺口返工。这部分收益没有量过，上面的倍数里没有扣。

## 实测

用 `evals/run_eval.py` 在真实的 `claude -p` 会话上量（模型 claude-sonnet-5-5，每个场景在全新的临时 git 仓库里跑）。"新增"= 新输入 + 缓存写 + 输出。

| 场景 | 组 | 次数 | 轮数 | 新增 | 缓存读 | USD |
|---|---|---|---|---|---|---|
| l0-typo | 不加载插件 | 5 | 3.0 | 5,241 | 92,006 | 0.0320 |
| l0-typo | 0.7.1 | 5 | 3.0 | 7,693 | 96,903 | 0.0423 |
| l0-typo | 0.9.0 | 5 | 3.0 | 8,067 | 97,629 | 0.0439 |
| l1-bugfix | 不加载插件 | 3 | 5.0 | 5,955 | 124,687 | 0.0393 |
| l1-bugfix | 0.9.0 | 3 | 6.7 | 9,674 | 157,584 | 0.0593 |
| classify-l3 | 不加载插件 | 3 | 2.7 | 6,290 | 59,840 | 0.0390 |
| classify-l3 | 0.9.0 | 3 | 1.0 | 8,176 | 27,666 | 0.0406 |

读法：

- **固定开销**：`l0-typo` 的任务几乎没有内容，三组轮数都是 3.0，新增的差额基本就是常驻规则的差额。0.9.0 比不加载插件多 2.8k，0.7.1 多 2.5k；**0.9.0 比 0.7.1 每个会话多约 0.37k（+4.9%）**。这是第一轮写缓存的钱，每个会话付一次。
- **小任务上插件更贵**：L0 新增 +54%、USD +37%；L1 新增 +62%、USD +51%（L1 多出约 1.7 轮，原因没有细查）。
- **判定场景持平**：`classify-l3` 三次都判成 L3 且没有改文件，USD 只多 4%。基线反而多花轮数去探索一个空仓库。
- **结论的边界**：只有三个场景，次数 3–5，一个模型；全部是 L0、L1 和判定，**没有任何 L2、L3 的实测**。L1 那一行里有一次出现过 1 次权限拒绝（输出里标了"用量不可信"）；此前另一批没有拒绝的 3 次是 6.0 轮 / 9,456 新增 / $0.0554，结论一致。

所以：和不用插件比，小任务上它花得更多，这一点现在有数据；L2、L3 是否更贵、贵多少、值不值，仍然只是估算。

## 这些变化借鉴自哪里

流程层面借鉴了 [superpowers](https://github.com/obra/superpowers) 6.2–6.4 的几个做法（只借思路，没有拷贝代码；对照的是 v7.0.0，bb92a77。省 token 的改动集中在 6.2.0 到 6.4.2，7.0.0 本身重做的是 brainstorming）：

- Native 执行：连续做完整个计划，只在最后对整个分支终审一次，取代逐任务审查。
- 计划只记录决策，不转录代码。
- 同形态的小任务合并成一次派发。
- 派给子 agent 的内容和它的回传都会常驻主会话上下文，长材料写成文件只传路径。
- 修复后不整体复审，只给 reviewer 修复的那段 diff。

superpowers 自己的节省数字（"计划耗时约四分之一、token 约三分之一""嵌套控制器成本约减半"）来自他们自己的 eval，是单个场景的结果，不能直接套到这里。

## 怎么用实测替换这份估算

挑几个真实任务，每个各跑一次"启用 dispatch"和"禁用 dispatch"，模型和 effort 保持一致，然后：

```bash
dispatch-usage 用工作流.jsonl 不用工作流.jsonl
```

同时记录是否通过同一套验收、返工了几轮、reviewer 抓到多少条"必须改"。只比 token 会漏掉审查带来的质量收益。
