- 日期：2026-09-23
- 来源：在 ashare-quant 会话里提出，使用者选择到本仓库新开会话来做
- 定级：**L3**。要改两个仓库（本插件、文档站 `~/workbench/lhanman.github.io`），新增一整块能力，一个会话做不完。使用者已同意按 L3 走。
- 下一步：`/dispatch:grill-me` 把下文"待定问题"问完，然后写规格。本仓库还没有 `openspec/`：需要的话先 `openspec init --tools claude`，或者把方案写在 `docs/plans/` 下。

## 使用者的原话
> lhanman.github.io 支持同步我知识库的 md 文档，成为一个我的知识库中心；每次 dispatch 沉淀知识库，也要同步到网站，网站首页能够高效美观地整理这些知识库。
> 也可以设计一些知识图谱之类的。
> 对于这类命中公司内容的不要上传。
> 还有，这个功能是可选的。

## 已确认的决策
0. **这是可选功能，默认关闭。**
   - 没开启时，`dispatch:note`、`dispatch-kb`、`dispatch-pages` 的行为和现在完全一样，也不要求配置文档站；
   - 开启后才同步知识库，比如在 `~/.claude/dispatch/config` 里加一个开关，或者配置了公开白名单就算开启。具体写法留给 grill-me 定。
   - 本插件还会给别人安装，没配置文档站、没有知识库的用户不能受影响。`dispatch:setup` 可以顺带问一句要不要开启。
1. **公开范围：按白名单公开。**文档站是公开的 GitHub Pages，做不了登录。
   - 只同步白名单目录，默认是「个人项目」「技术笔记」。
   - 单篇笔记可以在 frontmatter 里标记"不公开"，字段名待定。
   - 首页、搜索、知识图谱都只包含公开的笔记，不能从链接、标签、图谱节点里透露未公开笔记的标题。
2. **公司内容一律不上传，没有放行。**
   - 「云相册」「mimo」目录，以及每日工作计划，永远不上网。
   - 内容命中 `pages_deny`（DJI、云相册、mimo、MediaLoader、CloudMediaScheduler 等）的，整篇跳过，汇报里列出篇目和命中的词。
   - 不能用 `--allow` 放行，也不能为了上传而替换敏感词。
   - 拿不准是不是公司内容的，按不上传处理，再问使用者。
3. **自动同步。**`dispatch:note` 每写入一篇，都同步到网站。使用者早已授权文档站自动发布，不需要每次再问；但敏感检查不通过的，照样不发。
4. **要有知识图谱。**笔记之间的 `[[链接]]` 和共同标签连成关系网，可以点击跳转。

## 已查清的事实
- **知识库**：`~/workbench/lhan_doc`，GitHub 私有仓库 `Lhanman/lhan_doc`。一共 73 篇 md，按顶层目录分：fly 2 篇、mimo 10 篇、个人项目 13 篇、云相册 14 篇、技术笔记 1 篇、每日工作计划 16 篇（`copilot` 已排除）。只有 5 篇带 `summary`，4 篇是 `source: dispatch`，其余都是没有统一 frontmatter 的普通笔记。
- **文档站**：`~/workbench/lhanman.github.io`，GitHub 公开仓库。
  - 目前只有 5 篇 HTML 文档，都是 dispatch 相关的手册；
  - 目录页 `index.html`、`catalog.json`、`README.md` 由 `bin/dispatch-pages` 生成；
  - 部署：GitHub Actions `pages.yml` 运行 `.github/build-site.py`（37 行），按 catalog 把中文路径复制成 `p/<slug>/index.html`。
- **`bin/dispatch-pages`**（691 行 Python）已经有这些能力：
  - 敏感检查 `scan`：本机绝对路径、邮箱、疑似密钥、Artifact 专属能力、`pages_deny`；
  - catalog 维护、目录页生成 `build_index`、提交与推送；
  - 退出码：3 表示检查没过，4 表示推送失败。
- **配置**：`~/.claude/dispatch/config` 里有 `kb_dir`、`kb_exclude=copilot`、`pages_repo`、`pages_url`、`pages_title`、`pages_deny`。
- **笔记格式**：由 `skills/note/SKILL.md` 规定，包括 frontmatter 的 title/type/project/summary/tags/created/updated/source，四种类型（方案、决策、踩坑、指南），正文里用 `[[笔记名]]` 互相链接。

## 待定问题（留给 grill-me）
- 白名单配置的位置和写法（比如 `~/.claude/dispatch/config` 里加 `kb_public=个人项目,技术笔记`），以及单篇"不公开"或"强制公开"的 frontmatter 字段名。
- 「fly」目录归哪一边（内容未知，默认不公开，要问使用者）。
- Markdown 在哪一步渲染成网页：本地发布时渲染，还是 GitHub Actions 构建时渲染。另外还要处理 `[[链接]]` 的解析、链到未公开笔记时的处理、图片和附件、代码高亮。
- 网址方案：比如 `/kb/<slug>/`；中文标题怎么生成稳定的英文 slug；笔记改名后的处理。
- 首页信息架构：按项目、类型、标签、最近更新；搜索用前端索引；和现有 5 篇 HTML 文档怎么并存；深浅色和手机适配。
- 知识图谱：数据结构（`graph.json` 的节点和边，边来自链接或共同标签）、布局库（从 cdnjs 或 jsdelivr 引入），以及节点多了之后怎么保持可读。
- 老笔记缺摘要和标签：页面上按目录、标题、首段兜底，还是一次性补写 frontmatter。后者会改使用者的笔记，要先征得同意。
- 同步触发和删除：`dispatch:note` 写入后调用哪个命令（扩展 `dispatch-pages`，还是新增 `dispatch-kb publish`）；笔记更新了要重新发布；笔记删除或改为不公开时要从网站下线。
- 两个仓库的提交和推送顺序，以及推送失败的处理。
- 验证方式：用一个"含公司内容的假笔记"做测试，必须被拦截，不能出现在首页、搜索和图谱的任何地方。
