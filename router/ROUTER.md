# dispatch · 分级调度

开发类请求动手前，先按**风险最高的那个信号**定级。问答、调研、写文档等非开发请求直接处理，不定级、不写判定行；要发散想法（脑暴）时用 `dispatch:brainstorm`。

## 定级
- **L0 直做**：一句话能说清的改动（错字、配置值、重命名）。
- **L1 快修**：位置明确的 bug 或小功能，不超过 3 个文件，不碰公共接口。
- **L2 标准**：跨模块、需求有歧义、引入新依赖，或碰到公共接口、数据模型、并发、删除。
- **L3 特性**：一个会话做不完；改公共接口、持久化格式或数据迁移；新增一块完整能力。
- **L4 史诗**：新子系统或大改造，要先做架构决策，再拆成多个 L3。

L1 起，回复第一行写判定：`〔L2 · 依据〕`。L0–L2 判定后直接做；L3 以上先征得用户同意。

## 流程
- **L0**：直接改，跑最小验证。
- **L1**：先写三行意图（目标 / 不做什么 / 验收标准）。修 bug 先写能复现的测试；原因不明时用 `dispatch:systematic-debugging`。
- **L2**：范围不清先派 scout → 有未决问题则 `dispatch:grilling` 最多一轮 → Plan 模式出方案 → 按 `dispatch:test-driven-development` 实现 → 验证通过后按 `dispatch:code-review` 派 reviewer 审一次。方案写决策，不抄完整代码：测试写名字和断言，代码步骤写文件和签名，验证步骤写命令和预期输出；末尾列「审查重点」，至多 5 条需求隐含、却没有测试覆盖的输入或失败模式，审查时原文交给 reviewer。
- **L3**：`/dispatch:grill-me` → `/opsx:propose` → `dispatch:spec-check`（派 spec-checker 读规格，补缺口）→ 用户审规格 → `/clear` → `/opsx:apply` 按任务组执行，每组做完按 `dispatch:code-review` 审一次，通过后先提交该组代码，再在 tasks.md 勾掉该组，注明提交 SHA、审查结论和中途的裁决，勾选单独提交一次（规格同样列「审查重点」，随任务组交给 reviewer）；`/clear` 或压缩后先读 tasks.md 恢复进度，已勾掉的组不重做 → reviewer 终审一次（调用时指定 `model: opus`）→ `/opsx:verify` → `/opsx:archive`。项目没有 `openspec/` 时，建议运行 `/dispatch:setup`，或把方案写到 `docs/plans/`，进度同样记在方案里的任务清单上。
- **L4**：`/opsx:explore` 定决策 → 拆成多个 L3 逐个走。真正独立的部分才并行，最多 3 路，需要 git worktree。
- **界面改动**：L2、L3 改到前端界面时，在 `dispatch:code-review` 之外，再用 `impeccable`（已安装时）对改动的页面跑一次 `audit`：只修 P0/P1，不重新设计，修完不复审。

## 升降级
执行中随时重判，调整时说明原因。
- **升**：改动文件数超过预估 2 倍；出现架构决策；同一问题修了 2 轮没好（先转 `dispatch:systematic-debugging`，仍不行就 `/clear` 重写提示）；碰到公共接口、序列化或迁移；一个会话做不完。已有的意图和问答结论带入下一级，不重做。
- **降**：grilling 问不出未决问题；任务不足 3 项；摸底后发现只需改 1 个文件。
- **用户用 `#L` 指定的级别是下限**：不降到它以下。出现升级信号时先停下，说明信号和建议级别，请用户回复 `#L3` 这样的标记确认后再升。

## 子 agent
只在能节省主会话上下文、或需要独立判断时才派；派出时写清目标、输出格式、边界。
- `dispatch:scout`：要读 5 个以上文件或进入不熟悉的区域时用，优先于内置 Explore；小范围查找直接 Grep。
- `dispatch:reviewer`：按 `dispatch:code-review` 写委托，只给需求、改动范围和验证结果，不给会话历史。
- `dispatch:spec-checker`：L3 规格交给用户之前用 `dispatch:spec-check` 派一次，列出开工前还得问的问题。
- `dispatch:builder`：只接规格明确的机械性任务组，或 L4 的并行分支；需要判断的实现留在主会话。回报「受阻」时，补上下文、缩小任务或改规格后再派，或指定 `model: opus`，不要原样重派。

## 验证
命令取自项目 CLAUDE.md 的「dispatch 验证矩阵」。没有这一节时，从构建文件推断，并建议运行 `/dispatch:setup`。
一律通过 `dispatch-verify <命令>` 执行：完整日志写入文件，只回显结果摘要。验证没通过，不得声称完成；跑全量测试时，所有失败都要报告，包括不是本次改动引起的，不得挑着汇报。

## 上下文卫生
无关任务之间 `/clear`；到里程碑 `/compact`；同一问题纠正两次无效，就 `/clear` 重来。
